# FP技能検定 特訓アプリ 設計仕様書

3級・2級の2本のiOSアプリ。完全オフライン（サーバー通信・アカウント登録なし）の択一問題アプリ。
`C:\System_Dev\ITpassport`（ITパスポート特訓）の骨格を流用し、
出題ドメインをFP技能検定に差し替えたうえで、**1本のソースから2つのアプリを作る構成**にしたもの。

---

## 1. なぜ1リポジトリ2ターゲットなのか

3級と2級は App Store 上では別のアプリ（別バンドルID・別課金・別レビュー）である。
一方で、学習体験（間隔反復・解説パネル・習熟度・課金と試用）は完全に同じものを出したい。

| 案 | 採らなかった理由 |
| --- | --- |
| リポジトリを2つに分ける | 学習ロジックの修正を毎回2か所に当てることになる。必ず片方が古くなる |
| 1アプリで級を切り替える | 級は購入の単位にしたい。1アプリ内の切替にすると、3級だけ使う人にも2級の問題データを配ることになり、審査上も「何のアプリか」が曖昧になる |
| **1リポジトリ・2ターゲット（採用）** | ソースは1本、成果物は2つ。級の違いを `ExamFlavor` という1つの値型に閉じ込められる |

級によって変わるのは次の4つだけで、共通コードに「3級なら〜」という分岐は1つも無い。

| | 中身 |
| --- | --- |
| `FPn/AppFlavor.swift` | 表示名・バンドルID・課金プロダクトID・ID接頭辞・選択肢の数・試験制度の数値・法令基準日・公開URL |
| `FPn/Resources/` | 問題データ（`question_master_seed.json`）とアプリアイコン |
| `FPn/Info.plist` | ホーム画面に出るアプリ名（`CFBundleDisplayName`） |
| `FPn/Products.storekit` | シミュレータで価格を読ませるためのテスト用ストア |

`project.yml` は両ターゲットに `PRODUCT_MODULE_NAME: FPApp` を指定している。
モジュール名を揃えないと、テストの `@testable import` を級ごとに書き分けることになり、
テストコードまで級に依存してしまう（テストは1組を両方のターゲットで走らせる）。

## 3. 出題ドメイン

### 3.1 科目（`ExamField`）

学科試験は6科目から10問ずつ・計60問。**合否は60問の総得点だけで決まり、科目ごとの足切りは無い。**

1. ライフプランニングと資金計画
2. リスク管理
3. 金融資産運用
4. タックスプランニング
5. 不動産
6. 相続・事業承継

ITパスポート版では分野ごとに合格基準（各300点）があったため分野別習熟度が合否に直結していたが、
FPでは直結しない。それでも科目別習熟度をホームの主表示に置いているのは、
6科目が扱う制度が互いにほぼ独立していて、**手つかずの科目が1つあると本試験でそのまま10問落とす**ため。
「総合40%」からは次の手が決まらないが、「相続だけ10%」なら決まる。

### 3.2 細目（`MidCategory`）

40コード。3級と2級で**共通**にしてある。出題範囲の区分は両級で同じで、
違うのは問われる深さ（3級は制度の基本、2級は要件・例外・計算）だけなので、
級ごとに分けると同じ論点に別のコードが付き、問題データを級間で見比べられなくなる。

コード一覧は `docs/question-authoring-prompt.md` の細目コード表を参照。

### 3.3 出題形式（選択肢の数）

| 級 | 学科の形式 | `choiceCount` |
| --- | --- | --- |
| 3級 | ○×式 / 三答択一式 | 2 または 3 |
| 2級 | 四答択一式 | 4 |

`QuestionMaster` は選択肢を `choiceA`〜`choiceD` の固定プロパティで持ち、
実際に使う数を `choiceCount`（2〜4）が決める。配列にしていないのは、
SwiftDataの述語で扱いやすく、選択肢ごとの解説と1対1で並ぶため。

- **○×式は並べ替えない。** `A`=「正しい」、`B`=「誤り」で固定する。
  2択では並べ替えても測れるものは変わらないのに、○と×が毎回入れ替わると
  読み違いによる誤答を増やすだけになる
- **○×式では選択肢の記号（A/B）を出さない。** 「A 正しい / B 誤り」と並べると、
  選ぶべきものが記号なのか文言なのか一瞬迷う
- 3択・4択は毎回シャッフルする。固定順だと「この問題の答えは3番目」という
  位置記憶で解けてしまい、間隔反復が測るものが知識ではなく並び順の記憶になる

### 3.4 難易度（`QuestionDifficulty`）と課金の境界

| | 内容 | 無料 |
| --- | --- | --- |
| 1 基礎 | 制度の名称・数値をそのまま問う | ○ |
| 2 標準 | 要件・例外・適用の可否を問う（本試験の中心） | 試用期間中のみ |
| 3 応用 | 計算、複数制度の組合せ、実技レベル | 試用期間中のみ |

難易度は表示の目安であると同時に**課金の境界を兼ねる**。
2級は全体に難しいため「応用ばかり」になりがちだが、**基礎が0問になると
未購入の利用者が演習を1問も始められない**。収録比率の目安は 30 : 50 : 20 とし、
`scripts/validate_seed.py` が実際の比率を毎回報告する。
「基礎が1問もない」状態はユニットテスト（`testFreeTierHasQuestions`）で落とす。

## 4. データモデル

### 4.1 マスターと学習履歴の分離

`QuestionMaster`（マスター、Read-Only想定）と `UserProgress`（学習履歴、Read-Write）は
`questionId` (String) でのみ緩く紐付け、SwiftDataの `@Relationship` は張らない。

リレーションを張ると `QuestionMaster` の delete/upsert 時に `UserProgress` へ
カスケードが波及しうる。「マスターは総入れ替え、学習履歴は絶対保持」という要件上、
意図的に疎結合にしている。

アプリ更新時、同梱の `question_master_seed.json` の `version` が既適用バージョンより
新しければ `QuestionMasterSeeder` がマスターをUpsertする。`UserProgress` には一切触れないため、
問題データを総入れ替えしてもユーザーの進捗は保持される。

### 4.2 questionId は改名禁止

`<級>_<細目コード>_<4桁連番>`（例: `FP3_PENSION_0042`）。**公開後の改名は禁止**。
改名は「削除＋新規」になり、その問題の学習履歴が全ユーザーで失われる。
問題文・選択肢・解説の修正は自由（IDが同じなら履歴は保持される）。

接頭辞に級を入れてあるのは、**3級のデータを2級アプリに入れてしまう取り違えを機械で止める**ため。
問題文だけでは級の見分けがつかず、配信してから気付くことになる。
検査は3段構え（`validate_seed.py` / `SeedValidationTests` / TestFlightワークフローの
バンドル内容チェック）。

誤りが見つかった問題は、削除ではなくシードから外す。Seederは孤児進捗を許容する設計になっている。

### 4.3 法令基準日

FP技能検定は試験日ではなく**法令基準日時点の制度**で出題され、税制・社会保険の数値は毎年変わる。

- シードのトップレベルに `lawBasisDate`（`"2026-04-01"`）を持ち、問題ごとに上書きもできる
- 同じ値を `FPn/AppFlavor.swift` にも持ち、アプリの「このアプリについて」に表示する
- **両者が一致することをテストと検証スクリプトが確かめる。** ずれていると
  「2026年4月1日基準です」と表示しながら別の年度の数値を出題することになり、利用者は気付けない
- データ側はISO形式（`2026-04-01`）で持ち、画面には `LawBasisDate.display` が
  「2026年4月1日」に整形して出す。比較と並べ替えができる形を保つため

### 4.4 起動時の堅牢性

問題データが入らなくてもアプリが「起動しない」状態にはならないよう、次の方針を取っている
（ベースアプリから引き継いだ設計。理由込みで維持すること）。

- 適用済みシードバージョンは UserDefaults、実データは SwiftData と保存先が分かれるため、
  両者は食い違いうる。`QuestionMaster` が0件ならバージョンに関わらず再シードする
- バージョンの記録は `context.save()` が成功した**後**に行う。逆順にすると save 失敗時に
  「バージョンだけ進んで問題が空」の状態が永続化され、以降のシードがスキップされて復旧できなくなる
- シード失敗は `AppContainer` でログに記録するだけで、起動は継続する
- 永続ストアを開けない場合はインメモリにフォールバックする

## 5. 間隔反復（SRS）

出題順は `Services/Study/StudyQueue.swift` が決める。ランダム出題ではなく、次の優先度で並べる。

1. 復習期限が来た問題（間違えた問題・間隔が満了した問題）
2. まだ一度も解いていない問題
3. 期限前の問題（期限が近い順）

間隔は Leitner ボックス方式で、`UserProgress.reviewIntervalDays` の固定テーブル（0/1/3/7/14/30日）を使う。
正解すると1段階上がって間隔が伸び、間違えると段階0に戻ってその日のうちに再出題される。

「習得済み」は7日間隔の復習に正解して初めて付く。1回解けただけの問題は本番では解けないことが多く、
間隔をあけて再度正解できて初めて定着とみなすため。

## 6. 演習（クイズ）

- **1セット10問、制限時間なし。** 解説を読み込む学習体験と時間プレッシャーは両立しない
- **解答すると解説パネルが出て、そこで止まる。** 「次の問題へ」は解説の下に置く
  （解答ボタンと同じ位置に出すと、選択肢を押した勢いで解説を読まずに飛ばしてしまう）
- 解説は「正誤 → 自分が選んだ選択肢の解説 → 正解の解説 → 全選択肢の解説（折りたたみ）」の順。
  不正解のとき最も知りたいのは「なぜ自分の選択が違うのか」なので先頭に置く
- 結果画面では科目別の正答率を出す。合否に直結しないが、
  **次の出題範囲をどこに絞るか**を決められるのがこの表示の役目

## 7. 課金と試用

無料で配布し、買い切りのApp内課金で「標準問題（difficulty=2）」と「応用問題（difficulty=3）」を
出題対象に加える形にしている。**広告とサブスクリプションは実装しない。**

| | 価格 | プロダクトID |
| --- | --- | --- |
| 3級 | ¥300 | `com.eitango.fp3.unlock.advanced` |
| 2級 | ¥480 | `com.eitango.fp2.unlock.advanced` |

初回起動から7日間は全問を試せる。**期間が終わっても演習は使えるまま**で、
変わるのは出題対象が基礎の問題だけになること。問題一覧での閲覧・検索・解説の読み直しは常に全問できる。
機能を止める作りにしていないのは、一定期間後に動かなくなる体験版が App Review の拒否対象であり、
教育カテゴリでは「使えなくなった」という★1レビューを最も招くため。

### 判定の置き場所

| 型 | 役割 |
| --- | --- |
| `AccessRights` | 権利から出題できる難易度を決める値型。StoreKitにもUserDefaultsにも触れないのでそのままテストできる |
| `TrialManager` | 試用の起点をUserDefaultsに記録する。時計を戻して延長されないよう、観測済みの最新日時で判定する |
| `Entitlements` | StoreKitと試用をまとめ、画面に「いま何が出題できるか」を答える |

出題母集団（`QuestionRepository.fetchStudyPool`）は「ユーザーの設定（科目・難易度）」と
「権利」の**積**で決める。2つを1つのフラグに混ぜると、出題されない理由が設定なのか未購入なのかを
切り分けられず、画面の案内も出し分けられない。

`Transaction.updates` を購読して払い戻しを反映している。これを見ないと返金後も解放されたままになる。

## 8. 法的表示

金融商品・税制を扱うため、ITパスポート版より表示すべきことが多い。
`AppConfig` に文言をまとめ、「このアプリについて」と購入画面の両方に出す。

| 文言 | 目的 |
| --- | --- |
| `trademarkNotice` | FP技能検定は国家検定であり、指定試験機関（日本FP協会・金融財政事情研究会）と提携していないことの明示 |
| `disclaimer` | 個別の金融商品の勧誘・投資助言・税務相談ではないことの明示 |
| `lawBasisNotice` | 法令基準日より後の改正は反映されていないことの明示 |

App Store Connect のカテゴリは「教育」にする。金融・ファイナンスを選ぶと、
実際の資産管理や取引を行うアプリとして審査され、金融機関との関係や
投資助言の資格について説明を求められることがある。

## 9. 問題データの作り方とレビュー

1. `docs/question-authoring-prompt.md` のプロンプトに級・科目・細目・形式・難易度・問題数を埋めてAIに渡す
2. 出力を下記チェックリストで**人手レビュー**する
3. `batches/FP3/` または `batches/FP2/` に置き、`scripts/merge_questions.py` で取り込む（IDはここで採番）
4. `scripts/validate_seed.py` で機械検証し、必要なら `scripts/rebalance_answers.py` を掛ける

### 9.1 レビューチェックリスト（機械では検出できないもの）

- [ ] **数値が法令基準日時点のものか。** 毎年改定される額を使っていないか
- [ ] **計算問題を検算したか。** 式と数値が解説に書かれているか
- [ ] **正解が一意か。** 誤答のつもりの選択肢が、実は正しい記述になっていないか
      （FPは「正しいが問いに答えていない」選択肢を作りやすい）
- [ ] 誤答の解説が、その選択肢が指す制度の正しい内容を述べているか
- [ ] 制度名が正式名称か
- [ ] 3級の問題に4択が、2級の問題に2択・3択が混ざっていないか

### 9.2 機械検証（`scripts/validate_seed.py`）

級ごとの期待値（IDの接頭辞・ありえる選択肢の数・法令基準日）は
`FPn/AppFlavor.swift` から読む。ここに同じ値を書き写すと、片方だけ直したときに検証が素通りする。

落とすもの:

- IDの形式・重複・細目との不一致・級の接頭辞違い
- 科目と細目の対応の不一致
- 選択肢の数が級と合わない / Aから連続していない / 空 / 同じ文言
- 正解がその問題に存在しない選択肢を指している
- 解説の欠落 / 「正解。」「不正解。」で始まっていない
- 問題文300字・選択肢120字の超過、問題文の重複
- シードとAppFlavorの法令基準日の不一致

報告するだけのもの（警告）:

- 科目別・難易度別・形式別の収録数
- 正解の位置の偏り（選択肢の数ごとに、均等からの離れ具合で判定）
- ○×式で「正しい」が正解の問題の割合（半々が目安。偏ると読まずに当てられる）
- 正解だけが行数で最も長い問題の割合（内容を知らなくても当てられてしまう）

同じ検査は `FPAppTests/SeedValidationTests.swift` からも走る
（CIでスクリプトを回すだけだと、手元でシードを編集したときに気付けないため）。
